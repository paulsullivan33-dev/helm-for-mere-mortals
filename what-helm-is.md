# What Helm Is

Installing an application on Kubernetes
means handing the cluster a set of
**manifests**: YAML documents that each
describe one piece — a **Deployment**
that runs the program, a **Service**
that gives it a stable address, perhaps
a **ConfigMap** for its settings and an
account for it to run as. The pieces
refer to each other by name, they share
labels, and they differ from site to
site only in details: how many copies,
which version, what the greeting says.

**Helm is the tool that packages those
manifests so they can be reused.** A
Helm **chart** is a folder holding the
manifests as **templates** — YAML with
placeholders — plus a **values** file
that fills the placeholders in. Running
Helm over a chart is a small act of
substitution: templates plus values
become finished manifests, and those
manifests are what the cluster receives.
One chart, many sites; the differences
live in the values, where they can be
read, compared and kept in version
control.

A single run of Helm in this mode has a
name. When Helm installs a chart into a
cluster, that installation is a
**release**: the chart, the values it
was given, and a record of what was
applied, kept so the release can later
be upgraded or rolled back. Much of
this guide happens *before* any of
that: Helm can render a chart on your
own machine, with no cluster involved,
and show you exactly what *would* be
applied. That rendering is this guide's
home ground, because it is where charts
are written, read and checked.

## Why anyone would do this

- **Repetition without copying.**
  Without a chart, the second site means
  a second folder of YAML, edited by
  hand, drifting from the first. A chart
  keeps one source of truth and lets
  each site differ only in its values.
- **A handle on a whole application.**
  A release is one name for the whole
  bundle. Upgrading the application is
  one operation on the release, not six
  careful edits in the right order, and
  rolling back has a meaning.
- **Sharing.** A chart can be packaged
  into a single versioned file and
  published through a repository, so
  installing someone else's application
  becomes fetching their chart and
  supplying your values (chapter 10).
- **Reading before running.** Because
  rendering is local and free, you can
  see every manifest a chart will
  produce *before* a cluster is
  involved. Chapter 12 turns that into
  a habit.

## The trust rule, stated before everything else

A chart is not inert data. Its
templates are a small programming
language, and installing a chart means
asking a cluster — with your
credentials, at your privilege level —
to create whatever those templates
produce: workloads, accounts, roles,
network rules. A careless chart can
break things. A hostile chart can do
worse, and it does not need to be
obvious about it.

So this guide has one rule, and it is
not fine print:

> **Read a chart before you install
> it, and only ever install onto
> clusters that are yours to change.**

Reading is not a heroic demand here.
Chapters 5 and 12 show the working
method: `helm show` reads a chart
without installing anything, and
`helm template` shows you the finished
manifests, every line, before a
cluster is asked to accept them. If a
chart's author cannot be identified,
or the rendered output contains things
you cannot explain, the chart has not
earned your cluster. The lab in this
guide went further than most readers
will need to: it installed nothing at
all. Every chart it ran was written
for the guide or generated by Helm
itself, and every render happened on
the one machine.

## A first taste

After installing (chapter 3), the
whole idea fits in two commands:

```bash
helm create demo
helm template demo ./demo
```

The first asks Helm to write its
scaffold chart, a complete example
application. The second renders it —
release name `demo`, chart `./demo` —
and prints the manifests. Nothing was
installed; there is not even a cluster.
But the output is real, and chapter 4
reads it line by line.

Check: the render prints four
documents (the scaffold's account,
Service, Deployment and test pod by
default), each headed by a comment
naming the template it came from, as
in the lab's transcript
`helm-lab/transcripts/t02-scaffold-render.txt`:

```text
---
# Source: demo/templates/service.yaml
apiVersion: v1
kind: Service
```

## Who it is for

The person running a handful of
applications on a small cluster who is
tired of folders of near-identical
YAML. The team member handed "just
install this chart" who wants to know
what will actually happen. The chart
author packaging something of their
own so the next install — theirs or a
colleague's — is boring in the good
way.

## What it is not

Helm is not Kubernetes: it does not
run containers, schedule anything, or
heal failures; it prepares and tracks
manifests for the system that does.
It is not a configuration manager for
whole machines (chapter 13 gives the
neighbours their due). It is not a
guarantee: a chart renders the same
whether the result would thrive on a
cluster or be refused by it, and
chapter 14 is honest about that gap.
And it is not the only packaging idea
in town — plain manifests and Kustomize
(chapter 13) are respectable answers
that many teams prefer, and knowing
Helm includes knowing when not to
reach for it.
